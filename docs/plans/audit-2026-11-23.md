## Bitrate cap fix (2026-11-25)

Answers the open question from History M3 and M4 (the live table's green mark for average bitrate meant nothing when a focused and a capped quadrant played the same title).

- **Marks.** `bestSlots` skips `avgBitrateKbps` for a stream when its quadrants have different known caps; a cap that was not recorded (a run saved before caps were kept) counts as unknown, so old runs compare as before. `SummaryTable` says which quadrants were capped and suggests "uncapped". It applies to the live panel and a reopened run alike (`capOf` reads the last `abr-cap` for the quadrant; `rebuildRows` carries it).
- **Switch.** An "uncapped" checkbox in the player header lifts the 360p cap on every quadrant; "compare deliveries" and "compare transports" turn it on. The cap is still recorded per quadrant, so saved runs and charts describe what happened.
- **Not changed.** Segment time is also affected by the rung, and it is still marked when caps differ; startup and rebuffering are not affected the same way.
- **Browser check.** With the "compare transports" preset all four quadrants had no cap, played the same 2932 kbps rung and showed no note. Unticking "uncapped" capped Q2 to Q4 at 360p, showed "Q2, Q3, Q4 were capped at 360p while another quadrant on the same stream was not", and left the bitrate column unmarked while startup, segment time and throughput were still marked.
- **Found while checking, and fixed.** (1) Quadrants on `h1` showed `unknown` in the table and overlay: the summary re-normalised an already-normalised `h1`, which only `http/1.1` mapped to. The unit test used h2 and h3 only.
